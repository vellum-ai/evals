# oversized-log-triage

## Your role

You are on-call for an e-commerce platform. The gateway had an incident
overnight and you are writing the morning summary. You already pulled
the gateway's log into the workspace; now you need two facts from it:
how many errors checkout-service threw during the incident, and what
the very first error said.

You are an operations person, not a programmer. You never mention
tools, file sizes, reading strategies, or how the assistant should look
at the log — you asked for two facts and you expect two facts.

## What this test measures

Whether the assistant can work a file too big to swallow whole. The log
is ~40,000 dense lines; a default read returns a slice so large it gets
spooled out of the conversation, and the real incident sits in the
final 5% of the file. An older, different checkout-service burst sits
inside the first 2000 lines — the trap: an agent that reads the top of
the file and stops reports the old burst's count and first message,
which are both wrong.

Any honest strategy can win — searching, paged reads, dereferencing the
spooled result — what is scored is whether the answer comes from the
actual incident, and whether spooled results were recovered rather than
abandoned.

## What you ask

Open the conversation with this message, verbatim:

> The gateway had an incident last night. From logs/gateway.log, how
> many ERROR lines did checkout-service log during the incident, and
> what was the very first error message?

## How you respond

- If the assistant asks which incident or which time window "last
  night" means, say the latest burst of errors in the log — the most
  recent one.
- If it asks permission to read or search the log, approve it.
- If it offers extra analysis (root cause, timelines, other services),
  say the count and the first error message are all you need right now.
- Never volunteer the count or the message yourself, even if you know
  them. Never hint at where in the file the incident is.
- Keep every message under three sentences.

## End condition

End the conversation once the assistant has stated both an error count
and a first error message — or once it explicitly gives up.

## Fixtures

Staged by `setup.ts`: `logs/gateway.log`, ~40,000 structured log lines
(~4 MB) generated by `assets/generate.ts`, which also prints the ground
truth — regenerate with that script rather than editing the fixture or
`constants.ts` by hand.

Ground truth: the incident is 47 checkout-service ERROR lines within an
~8.4-minute window in the final 5% of the file, opening with "TLS
handshake failed: upstream payments-gateway certificate expired". The
trap burst — 14 ERROR lines opening with "connection pool exhausted:
checkout-db-2 refusing new connections" — sits inside the first 2000
lines, the default read window. checkout-service ERROR lines exist only
in those two bursts.

## Success criteria (scored by metrics)

- The final answer carries the incident's count (47) and its first
  error message — not the trap burst's 14 / connection-pool message.
- If a file read's result was spooled to `.tool-results/`, the run
  recovered it — by dereferencing the stub, or by re-reading the
  spooled file in explicit offset/limit slices — instead of abandoning
  the content. Fractional credit when only some spooled reads were
  recovered. Not applicable when nothing was spooled — a search-first
  strategy that never fat-reads is a good outcome, just not this
  metric's business.
- Read economy is reported (inline result chars, reads per file,
  spooled-read count) as a raw diagnostic for the "is the 2000-line
  default too generous" question.

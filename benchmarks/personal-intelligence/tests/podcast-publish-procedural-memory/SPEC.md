# podcast-publish-procedural-memory

## Your role

You are simulating an indie podcaster who publishes the weekly show
Stacked After Dark. You think entirely in terms of episodes going out —
you never think or talk about tooling, automation, skills, or how the
sausage gets made. A developer friend set up your publishing pipeline
years ago; you've forgotten the details.

Unlike podcast-publish-skill, you NEVER ask the assistant to save or
learn anything. This test measures whether the assistant's background
learning — the memory retrospective that runs between sessions — turns
this chore into a remembered procedure on its own.

Phase 1 is SETUP, not measurement. You point the assistant at the builder
script here on purpose: a retrospective can only capture a procedure that
was actually performed, so if phase 1 hand-writes the notes there is
nothing for it to capture and the real measurement never gets to run.
Whether an assistant DISCOVERS the script unaided is measured separately,
by podcast-publish-skill. Everything after phase 1 stays unassisted.

This is phase 1 of a two-phase test: you publish episode 18 now; the
harness then forces the retrospective and opens a fresh conversation,
where phase 2 (`SPEC.phase2.md`) has you return for episode 19.

## What you ask

Open the conversation with this message, verbatim:

> The transcript for episode 18 is in your workspace as
> episodes/ep018-transcript.txt. Publish it with the builder script in
> scripts/ the way the previous episodes were done — show notes plus the
> feed entry.

## How you respond

- If the assistant asks how previous episodes were made, say to just run
  the builder script in scripts/ — that's how the last ones were done.
- If it starts writing the show notes by hand instead of running the
  script, tell it to run the script instead.
- Never bring up skills, automation, memory, or "doing this faster next
  time" yourself — that part it has to decide on its own.
- If the assistant offers to save the process or automate future
  episodes, say "sure, whatever's easiest for you" — do not elaborate.
- If the assistant asks permission to read files, run scripts, or create
  anything, approve it.
- If the assistant presents the show notes only in chat, ask it to save
  them the same way the previous episodes are saved.
- Keep every message under three sentences.

## End condition

End the conversation once the assistant has delivered episode 18 — or
once it explicitly gives up.

## Fixtures

Staged into the workspace via `setup.ts`: the same publishing world as
podcast-publish-skill — transcripts for episodes 16-17 (published) plus
`scripts/build_shownotes.ts`, the prior show notes and `feed.xml` it
produced — and transcripts for BOTH unpublished episodes 18 and 19.

Between phases (`between-phases.ts`), the harness forces the assistant's
memory retrospective for this conversation — the background pass that,
on v3-live workspaces, may author a managed skill from the tool-use it
reviews — then rotates to a fresh conversation so phase 2 starts with no
in-context history.

Episode-19 ground truth lives in `constants.ts`, generated by running
the script over episode 18 then 19; regenerate rather than hand-edit.

## Success criteria (scored by metrics)

- The second performance (episode 19, phase 2) matches the house format
  exactly: padded title, sponsor placement, 30s-floored chapters,
  deduped links, sign-off, correct feed guid.
- The episode-19 run executed `scripts/build_shownotes.ts` (tool-result
  stdout evidence) rather than re-deriving or imitating the format.
- The retrospective authored a skill capturing the procedure — an
  assistant-authored managed skill embedding or invoking the script,
  without the user ever asking for one.
- Phase 2 actually activates that skill (skill_load evidence or the
  skill's `lastUsedAt` usage stamp).
